Lens: frontend robustness, state/race bugs, swallowed errors, UX (local bar). Reviewed
2026-09-18 at commit `8ac2758`. No files modified.

---

Adversarial frontend/UX review of the dsagent-v2 UI. Findings ranked by severity, each with file:line, repro, and fix. Nothing modified.

=== CRITICAL ===

C1. Transient getSession failure WIPES an existing chat to empty — silent data loss.
ChatCenter.tsx:232-240. The outer fetch's `.catch` treats ANY error identically to "this chat doesn't exist yet": it sets initial=[] AND fires `api.saveSession(id, {title:"", messages:[]})`. That catch cannot tell a 404 (genuinely new chat) from a 500 / network blip / server restart on an EXISTING chat. Repro: open a chat with history → server hiccups (or you're briefly offline) on the GET → the code assumes it's a new empty chat and PUTs messages:[] over the real transcript. The whole conversation is gone server-side. Fix: only register-empty on a real 404. Have api.getSession throw a typed error carrying res.status (json() already has it at api.ts:13-18) and in the catch do `if (err.status === 404) { register empty } else { setInitial([]) WITHOUT the destructive save, and surface an error }`. Never PUT an empty transcript on an unknown/transient error.

=== HIGH ===

H1. sessions-load effect has no in-flight cancellation → a stale response clobbers what the user just did. THIS IS THE ROOT CAUSE of both manual-test bugs (dropped typing + New-chat-doesn't-switch).
App.tsx:59-76. Unlike every other fetch effect in the codebase (ChatCenter.tsx:224, Sidebar.tsx:50, SessionRuns, ProjectArtifacts all use a `live` flag), this effect has NO cleanup and NO guard. Its `setActive` updater closes over the effect-run's own `activeProjectId` and `convs`. StrictMode (main.tsx wraps <App/> in StrictMode) double-invokes it in dev, and the projects() effect (App.tsx:38-49) can correct activeProjectId right after load, so two `api.sessions()` calls are commonly in flight at once.
  - Bug (b) "New chat doesn't switch on first click": user clicks New chat → active = new conv (App.tsx:97). A still-in-flight sessions() from before the project settled resolves late; its updater sees `cur.projectId === activeProjectId(old closure)` = false → REPLACES active with the old project's convs[0]. The user's New-chat click is silently undone.
  - Bug (a) "typing right after reload gets dropped / doesn't send": same late setActive swaps `active` to a different conversation object with a different id → App.tsx:166 `key={active.id}` changes → ChatCenter + ChatThread remount → the composer (and any in-flight send targeting the old thread) is destroyed, and half-typed characters are lost.
  Fix: add the standard guard — `let live = true; ...then(...=> { if (!live) return; ... }); return () => { live = false; }`. That single change fixes both reported bugs. Also fold the projects() correction so sessions only fetches once the project id is settled, to avoid the redundant first fetch.

H2. Model-written HTML reports open as a live page in the APP's OWN origin — stored-XSS surface.
ChatCenter.tsx:196-204 (ProjectArtifacts) + api.ts:97-98 (projectFileUrl). Artifacts link to `/projects/{id}/files/{path}` with target=_blank; the comment says HTML "opens in its own tab" deliberately. That HTML is written by the model (and may embed data it ingested from a dataset). Served same-origin, its <script> runs with full access to the app origin: it can call /sessions, /projects, delete or exfiltrate every chat, read localStorage. rel="noreferrer" does nothing against same-origin execution. Repro: a report (or a dataset row the model echoes into one) contains `<script>fetch('/sessions/...',{method:'DELETE'})</script>` → user clicks the artifact chip → it runs. Fix (server-side, but the UI intent drives it): serve project files with `Content-Disposition: attachment` (download, don't execute), or from a distinct sandboxed origin, or wrap in a sandboxed iframe with a strict CSP. Do not navigate the app origin to attacker-influenceable HTML.

H3. keepalive save silently drops the last turn of a long chat, and mis-fires on plain chat-switch.
ChatCenter.tsx:299-324 + api.ts:79-86. `flush()` always calls `save(true)` (keepalive), used both on `pagehide` (unmount) AND on switch-away (the effect cleanup at :348). Two problems: (1) keepalive bodies are capped at ~64KB by the browser; a long transcript — especially with inline Vega `data.values` — exceeds that, so the unload save is rejected and the last turn is lost on reload/close (the `.catch` sets dirty=true but the page is already gone). (2) On an ordinary chat switch the page is NOT unloading, yet flush still uses keepalive, so a large chat's save can hit the 64KB cap and fail where a normal fetch would have succeeded. Fix: use keepalive ONLY on the real pagehide path; the unmount-on-switch flush should be a normal fetch (can be awaited/allowed to finish). For genuinely large transcripts on unload, consider navigator.sendBeacon with a compact payload or accept that giant transcripts can't flush on unload and save more aggressively during the session.

=== MEDIUM ===

M1. Chat rows are non-interactive divs. Sidebar.tsx:83-102 — `<div onClick=...>` with no role/tabIndex/keydown. Not keyboard- or screen-reader-accessible (the ✕ inside is a real button, but selecting a chat isn't). Fix: make the row a <button> (move the ✕ out of the button, or use role="button" + tabIndex + Enter/Space handler).

M2. Every failed write is swallowed with zero user feedback. saveSession (ChatCenter.tsx:314 — chat fails to persist, user never told), deleteSession (App.tsx:106 — optimistic remove; if the server delete fails the chat reappears on next poll with no explanation), ProjectSwitcher create() (ProjectSwitcher.tsx:37 — click Crear, nothing happens on failure), DatasetsSection upload/remove (DatasetsSection.tsx:24,34). The polling `.catch(()=>{})` in SessionRuns/ProjectArtifacts/Sidebar are acceptable, but the user-initiated writes need at least a toast/inline error. Worst is the save-failure silence given C1/H3 also cause data loss.

M3. ChartView re-embeds on every parent re-render. ChatCenter.tsx:47-57 `JSON.parse` produces a NEW spec object identity each render; ChartView.tsx:19 effect deps `[spec]` → full vega re-embed on every re-render of the assistant message (e.g., each streamed token of text following the chart). Flicker + wasted work. Fix: memoize the parsed spec (useMemo keyed on the raw fenced string), or compare by stringified content.

M4. Huge inline Vega spec can freeze the tab. ChatCenter.tsx:48 `JSON.parse(m[1])` on a multi-MB `data.values` blob runs synchronously on the main thread, then vega renders it. VIZ_INSTRUCTIONS ask the model to aggregate, but a misbehaving model isn't bounded. Fix: cap m[1].length before parsing and render a "chart too large" fallback.

M5. ProjectArtifacts is project-scoped but presented per-chat and implies "this chat made these." ChatCenter.tsx:177-210, label "Archivos del proyecto" sits right above the composer in every chat, showing files any chat in the project produced. Also it returns null both while loading and when empty, so the user can't tell "loading" from "none." Plus it polls every 5s forever, alongside SessionRuns (4s) and Sidebar runs (4s), with no `document.hidden` gating — needless network/battery when the tab is backgrounded. Fix: clarify the label/scope, add a distinct empty vs loading state, and pause polling on visibilitychange.

M6. No error boundary anywhere. main.tsx / App.tsx have no <ErrorBoundary>. A throw in MarkdownText/ChartView/marked takes down the entire SPA to a white screen. Fix: wrap the app (and ideally each message) in an error boundary.

Worth confirming the server tie-breaks on updated_at, not arrival.
