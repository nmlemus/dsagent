# Round 2 — saas-tenancy (Fable 5.1) — verbatim (head + parts 1–3)

Lens: tenancy isolation matrix across 12 dimensions, end-to-end request trace, the
`default`/legacy hazard, runner vs job-queue/object-storage fit, target SaaS architecture,
ordered migration. Reviewed 2026-09-19 at commit `8ac2758`. No files modified.

Effort: S <1 wk · M 1–3 wk · L 1–2 mo · XL >2 mo. Path: SaaS / self-host / both.

---

**Verdict up front.** Today this is a single-process, single-principal, local-filesystem application in which the browser picks its own identity (`thread_id`, `project_id`, `run_id`) and model-generated code runs on the API host with the platform's own secrets in its environment. None of that is a bug in the localhost dev tool; all of it is disqualifying for a hosted SaaS, and most of it also disqualifies a self-hosted product because a customer's *users* are not one principal either. The good news is structural: the runner's contract (declared DAG, `RunState` as a self-contained JSON document, gates persisted in `run.json`, `produces` verified on disk) is compatible with a worker tier; what is not compatible is everything wrapped around it in `serve.py`/`driver.py`.

### Remaining matrix rows (part 1/3)

DATA IN TRANSIT — Today: `cli.py:339` uvicorn plain HTTP on 127.0.0.1; no TrustedHost/Host validation; no CORS config (works only because SPA is same-origin, `ui/vite.config.ts` proxies to localhost:8000); `serve.py:547-553` `/projects/{id}/files/{path}` serves model-written files same-origin with NO CSP (unlike `/runs-x`, `serve.py:440-486`). Assumption: localhost; DNS rebinding possible now; the day an auth cookie exists, a model-authored HTML file on that route is session-stealing XSS. Requires: TLS at edge, TrustedHostMiddleware, CSP on every model-authored response, artifacts on a separate origin or signed URLs. Change: proxy TLS + trusted-host + CSP middleware; move all model-file serving to the sandboxed prefix or an artifacts origin. Effort S. REQUIRED, both paths — must land together with auth.

COMPUTE (LLM-written code) — Today: kernel env `envs/kernel.py:87` `LocalShellBackend(root_dir=workspace, virtual_mode=True, inherit_env=True)`; deepagents `local_shell.py:227-231` documents "no sandboxing … access any file on the filesystem regardless of virtual_mode"; `JupyterKernel` (`kernel.py:26-34`) is a host process inheriting os.environ. Docker env `docker.py:99-120`: host bind-mount, `--gpus all`, no `--network/--memory/--cpus/--pids-limit/--cap-drop/--security-opt`; needs the docker socket on the API host (root-equivalent); `ensure_image` builds Dockerfiles on that daemon (`docker.py:243-256`). Skill scripts and auto-gate checks run through `env.backend.execute` (`host/build.py:122-123`, `runner.py:966`) — i.e. on the host for kernel envs. `Step.timeout` (`models.py:60`; `fit: 4h` in mmm-meridian) is never read by the runner. Assumption: "the model's code is my code". Requires: per-tenant sandbox with own FS view, cgroup limits, timeouts, no host, no platform secrets; the kernel must live INSIDE the sandbox. Change: kernel-in-sandbox (ipykernel inside container/microVM driven over the sandbox exec channel or a kernel gateway) — architecture.md §3.4 already anticipates `kind: modal`; harden Docker (gVisor/Kata/Firecracker runtime, `--network none` + egress proxy, cgroups, `--cap-drop ALL`, read-only root, pids limit, GPU by device index); enforce `Step.timeout` + per-run wall/$ budgets in the runner. Effort XL (SaaS) / L (self-host). BLOCKER, both.

NETWORK EGRESS — Today: unrestricted; kernel = host network; Docker default bridge (`docker.py:108-120`). Requires: default-deny egress, per-tenant allowlist (PyPI mirror, approved connectors), no cloud metadata endpoint, no reach to API/DB/Redis. Change: sandbox network policy + egress proxy; connector creds brokered per run, never ambient. Effort M (rides on sandbox work). BLOCKER SaaS / REQUIRED self-host.

SECRETS / API KEYS — Today: provider key ambient in the server process (`.env` at repo root loaded by the shell; `models.py:17-19` global `DSAGENT_MODEL`); `inherit_env=True` copies the ENTIRE process env, ANTHROPIC_API_KEY included, into every `execute` the model issues (`local_shell.py:196-198`); the Jupyter kernel gets the same. Cost is recorded post hoc only (`runner.py:725`). Assumption: one key, one payer, key on the same box as code that can `print(os.environ)`. Requires: platform keys never enter the sandbox; per-tenant BYOK optional; spend metering with hard caps before admission. Change: `inherit_env=False` + explicit allowlist and scrubbed kernel env (S, do now); LLM calls only from API/worker tier; secret manager; metering ledger from run.json telemetry → pre-run quota checks (M). BLOCKER.

CONFIGURATION — Today: cartridge fixed at process start (`cli.py:320`); `serve.py:252` `cartridges[0].envs["default"]` hard-coded; `Project.cartridge` (`projects.py:38`) exists but is ignored everywhere; model override is global env or persona frontmatter; `prices.yaml` searched upward from cwd (`pricing.py:123`); `globals()["RunAgentInput"]` hack (`serve.py:278-279`). Requires: per-tenant cartridge version, model allowlist, BYOK, quotas, flags, region. Change: tenant/project config table; resolve cartridge+env from `project.cartridge` (versioned, immutable); enforce model allowlist when building agents. Effort M. REQUIRED.

QUOTAS / RATE LIMITS — Today: none. Only ceiling is `RECURSION_LIMIT=150` per turn (`serve.py:39`). Upload bodies unbounded (`api.py:294`, `api_projects.py:67`); `seed_run` copies the whole dataset dir per run AND per chat turn (`serve.py:271`); kernel per-call timeout 600s (`kernel.py:26`), docker exec 3600s (`docker.py:51`); no step/run/tenant budget; no cap on concurrent runs (`driver.py:310-316` one thread per run). Requires: per-tenant caps on concurrent runs, GPU-hours, tokens/$, storage, upload size, request rate; admission control before enqueue. Change: quota service in front of POST /runs, /agent, uploads; worker enforces step timeout and cost budget; storage accounting; seed by reference not copy. Effort M. REQUIRED.

BACKGROUND JOBS (runs, up to 4h GPU) — Today: launcher runs are daemon threads INSIDE the API process (`driver.py:310-316`); `_threads` dict is the only liveness record (`driver.py:284-286`; `runs.py:60-65` admits run.json cannot tell running from died). Chat-started runs: `tools.py:149-164` executes the ENTIRE workflow synchronously inside the AG-UI HTTP request — the SSE stream is the run's lifetime. The driver wraps every launcher run in the orchestrator graph with a SQLite checkpoint in the default workspace (`serve.py:305-308`, `serve.py:393-403`) and then needs `_walk_past_decided_gates` (`driver.py:239-270`). Shutdown kills threads mid-step. Requires: durable queue, leased workers with heartbeats, resume on any worker, survive deploys, GPU scheduling, cancellation, timeouts. Change: worker tier calling `WorkflowRunner` DIRECTLY (the CLI path, `cli.py:226-233`) with `ask_human` = "persist pending gate, exit cleanly"; gate answer = enqueue resume job; drop orchestrator wrapping for launcher runs (deletes the walk-past-gates dance and the sync/async checkpointer split); chat's `run_workflow` becomes enqueue + return run_id. Effort L. BLOCKER.

STREAMING (SSE / AG-UI) — Today: `/runs/{id}/events` polls `events.jsonl` on local disk every 250ms per client (`api.py:435-453`); `/agent` clones a cached per-project agent and streams from an in-process graph (`serve.py:289-296`). Assumption stated in `api.py:64-70`: reader and writer are the same process on the same disk. Requires: fan-out across replicas; workers elsewhere publish; reconnect by cursor. Change: events to a durable stream (Postgres table or Redis Streams) keyed (tenant, run_id, index); API subscribes; AG-UI endpoint builds per-request agents over a shared DB checkpointer. Effort M. REQUIRED (SaaS).

CACHES / IN-MEMORY STATE — Today: `serve.py:254-272` `chat_agents`/`chat_envs`: one live host kernel + one `InMemorySaver` per project, never evicted, the saver accumulating every thread's checkpoints; env built inside the request (blocks the loop); one kernel shared by all concurrent turns of a project (`kernel.py:98-101` nonlocal kernel); `driver._threads/_errors`; `attempts` dict in `amend_tools` (`charts.py:433`). Requires: no tenant-affine state in the API process; horizontal scaling; kernel lifecycle bounded by session/idle TTL. Change: stateless API; `AsyncPostgresSaver`; sandbox/kernel sessions in a sandbox manager with idle TTL and per-tenant caps; no long-lived agent cache. Effort M. BLOCKER for >1 replica.

## 2. End-to-end trace, `default` hazard, runner fit (part 2/3)

END-TO-END TRACE (every point where tenant identity is absent [A] or client-trusted [C], or data/compute crosses [X]):
1. Browser mints identity. `ui/src/lib/conversations.ts:15` `crypto.randomUUID()` becomes thread_id = session id; `ChatCenter.tsx:232-239` `PUT /sessions/{uuid}` with `{project}` read from the UI's localStorage (`App.tsx:19`). [A][C] Any client can also re-PUT ANY existing session id into ANY project and overwrite its messages wholesale (`api_projects.py:105-115`), and enumerate everything: GET /projects (`api_projects.py:21-23`) → GET /projects/{p}/sessions → GET /sessions/{id} returns full transcripts (`api_projects.py:86-91`).
2. `agent_endpoint` `serve.py:287-289`: `project_id = sessions.project_of(thread_id)`; unregistered thread → "default" (`sessions.py:64-66`). [A][X] Unknown threads silently land in the shared default bucket.
3. `chat_agent_for(project_id)` `serve.py:257-272`: first call runs `make_env` synchronously in the request → starts a HOST Jupyter kernel and a `LocalShellBackend(inherit_env=True)`; cached forever. Every subsequent call `seed_run`s the project's datasets into the chat workspace (full copy per turn). [X] Compute is per-project but on the host with the platform's secrets in env; concurrent turns of one project share one kernel (`kernel.py:98-101`) so users see each other's variables; `virtual_mode` is documented as no security (`local_shell.py:231`), so `os.listdir("../..")` from run_python reaches every other project's workspace.
4. Orchestrator tools (`serve.py:210-214` → `tools.py:94-210`): `run_workflow` resolves the run dir from thread_id via `session_project` (`tools.py:89-91`) — fine — but `list_run_files`/`read_run_file` (`tools.py:178-207`) and `amend_tools` (`charts.py:436, 465, 487`) take the DEFAULT `runs_dir` and any `run_id`. [X] The model, prompted by the user, can read or amend any run in the default project regardless of the caller's project; with projects-as-tenants this is cross-tenant read/write by the LLM.
5. `run_workflow` executes the run in-request (`tools.py:164`); a human gate raises `interrupt()` (`serve.py:127`) into an InMemorySaver — lost on restart, i.e. on every deploy; a 4h Meridian fit cannot live inside an SSE request behind any load balancer.
6. Files written: run workspace `<project>/runs/<id>/workspace` (`tools.py:89-91`); chat artifacts in the project workspace (`serve.py:189-192`). Served by `/runs/{id}/files/…` (`serve.py:478-481`) and `/projects/{id}/files/…` (`serve.py:547-553`) with no principal check [A], the latter with no CSP.
7. Launcher runs (`api.py:209-244` → `driver.start`): `mark_session(run_dir, body["session"])` is client-controlled linkage [C]; run ids are guessable `f"{workflow}-{YYYYmmdd-HHMMSS}"` (`api.py:151`) [C]; `run_dir_of` resolves any run id across all projects via `store.locate_run` with no project check (`api.py:165-176`, `projects.py:77-93`) [A][X]; and the run is driven through the ONE orchestrator built for the default project's env and workspace (`serve.py:305-308`), so a launcher run for project B goes through an orchestrator whose execute/run_python/read_file are rooted in `.dsagent/serve` and whose checkpoint SQLite lives there (`serve.py:393`). [X] This is the concrete cross-project compute leak that exists today.

THE `default` PROJECT + LEGACY `.dsagent/serve` ADOPTION:
- `ProjectStore.runs_dir("default")` returns the flat legacy dir (`projects.py:67-72`); `locate_run` searches it FIRST (`projects.py:83-85`); `GET /runs` lists only it (`api.py:190-192`); every unregistered thread maps to it (`sessions.py:66`); `project_workspace("default")` is the server's `--workspace` (`serve.py:189-192`); the default chat env is the process-global env (`serve.py:261`, `cli.py:322`) and is ALSO the driver's env for all launcher runs.
- Under any multi-user deployment `default` is a shared catch-all with a shared kernel, shared workspace and guessable run ids. Default-first search means a run-id collision between two projects resolves silently to the legacy dir. `_slug` project ids (`projects.py:45-47`) collide across tenants by construction ("Sales" → sales, sales-2).
- Required: there is no `default` in SaaS. Every principal gets an explicit home project at signup; legacy adoption becomes a one-time `dsagent migrate` for self-host, after which `runs_dir(project)` has one rule. Unregistered thread → 401/404, never a fallback. Project and run ids become ULIDs; names are display-only. Effort S–M. BLOCKER (SaaS).

RUNNER vs JOB QUEUE + WORKERS + OBJECT STORAGE:
Compatible, keep: `RunState` is a self-describing JSON doc with atomic writes (`runner.py:273-292`); steps resume by `status != "done"` (`runner.py:562`); the pending human gate is persisted BEFORE asking (`runner.py:867-872`) and rejection sends the step back with the note (`runner.py:886-903`); produces verification and telemetry are per step and local to the executing process; envs are provisioned lazily per run (`runner.py:509-514`). A worker on any host can run `WorkflowRunner.run(resume=True)` given the run dir — the CLI already does exactly this (`cli.py:226-233`).
Assumes a local shared filesystem, must change: the run dir is the medium between runner and API — `events.jsonl` appended (`runner.py:367`) and polled by the API (`api.py:441`); `STOP_FILE` written by the API (`api.py:390`) and polled by the runner (`runner.py:597`); run.json read on every list; `GATE_VERSIONS` copies (`runner.py:905-933`); `resolve_run_file`/FileResponse (`serve.py:408-437`); `driver.is_running` in-process (`driver.py:284`). Datasets copied host-side (`datasets.py:53-66`); seeds `shutil.copytree` (`tools.py:156`); skills materialized per workspace (`build.py:41-73`); Docker bind-mounts a HOST path (`docker.py:110-113`) so the docker host must hold the workspace; chart validation reads the workspace in the harness process (`charts.py:238-248`) — right on a worker, wrong on the API; `locate_run` walks the projects root per request (`projects.py:86-92`). The serve-mode gate is a LangGraph interrupt inside a checkpointed orchestrator graph (`serve.py:114-129`, `driver.py:293-297`) with thread `run:<id>` in a SQLite file inside the default workspace — the one piece that cannot move to a worker as-is, and also unnecessary once launcher runs stop going through the orchestrator.
Concrete runner target: worker hydrates seed/workspace from object storage into local scratch → runs `WorkflowRunner` with `on_event` publishing to a stream and `ask_human` = persist gate + raise a `GatePause` that ends the job cleanly → uploads the workspace (or only changed files, which telemetry already lists at `runner.py:692`) at each step boundary and on pause/end → `POST /runs/{id}/gate` writes the decision and enqueues a resume job. Stop = a DB flag read in `_stopped`. Liveness = job lease + heartbeat. That touches `runner.py` in three small places (`_stopped`, storage hooks around `env_for`/step end, a pausing `ask_human`) and deletes `driver.py`'s graph wrapping. Gates stay runner-level (invariant 4 intact); produces stays verified on the worker's disk before upload (invariant 5 intact).

CARTRIDGE PROVISIONING: loaded once from a path (`cli.py:320`), shared by every request, `cartridges[0]` assumed (`serve.py:252`), `Project.cartridge` dead. Skill CONTENT copied into each workspace (`build.py:41-73`) is fine — immutable bytes inside the tenant's mount. But a cartridge carries executable code (skill scripts, gate checks, Dockerfile): platform-owned = trusted; tenant-uploaded = untrusted and may only execute inside that tenant's sandbox. Today `run_skill_script` and `_auto_gate` execute via `env.backend`, which for `kind: kernel` IS the host (`kernel.py:87`) — so no tenant cartridges until the kernel is in the sandbox; tenant Dockerfiles need a remote builder (Kaniko/BuildKit) with size/time limits. Required: versioned, content-addressed cartridge registry (signed for platform tier, scanned for tenant tier); `project.cartridge = "ds@0.1.0"` resolved per run/turn; images pre-built per version and pulled, never built at request time. Effort M (+ the sandbox dependency).

## 3. Target architecture, migration, blockers, phases (part 3/3)

TARGET ARCHITECTURE (SaaS):
- Edge: TLS, WAF, OIDC/SSO, rate limit, TrustedHost → Principal{tenant_id, user_id, roles} on every request.
- API tier (FastAPI, N stateless replicas): `/agent` builds a per-request orchestrator with a Postgres checkpointer keyed (tenant, thread); tools bound to the principal from `configurable`, never from thread_id; `run_workflow` only enqueues. `/projects /sessions /runs /datasets` are Postgres rows with tenant_id; artifacts via signed URLs on a separate origin. `/runs/{id}/events` subscribes to the event stream. Quota + metering checks before any model call or job.
- Postgres: tenants, users, projects, sessions (one row per message, server sequence), runs (RunState json + version), gate_decisions (who/when — the audit trail), events, usage_ledger, cartridge_versions, LangGraph checkpoints.
- Object storage: s3://<tenant>/<project>/{data, chat-workspace, runs/<id>/workspace, gate-versions}, per-tenant KMS key, TTLs.
- Queue: run jobs {tenant, run_id, resume, gate_answer?}; CPU and GPU lanes; leases + heartbeats.
- Worker tier: pull job → hydrate scratch → `WorkflowRunner` with ask_human = persist gate + exit, on_event → stream, enforced Step.timeout and $ budget; env = SandboxBackend (gVisor/Kata/Firecracker or Modal/E2B/Daytona) with the workspace mounted, ipykernel INSIDE the sandbox, egress default-deny, no secrets in env; upload changed files per step; emit dsagent.env with image digest.
- Sandbox manager: chat sandboxes per (tenant, thread) with idle TTL and per-tenant caps — no shared kernels, ever.
- Secrets: platform LLM keys in a secret manager, used only by API/worker; tenant BYOK; connector creds brokered per run.
- Cartridge registry: versioned, content-addressed, platform-signed; images pre-built per version.
- Observability: OTel traces/logs/metrics tagged tenant/run/step; audit log for gate answers, deletes, uploads.
Isolation per layer: identity at the edge; authorization = row-level tenant_id + scoped queries; storage = prefix + KMS per tenant; compute = one sandbox per run/thread; network = per-sandbox egress policy; secrets never cross the sandbox boundary; quotas = admission control; streaming = tenant-scoped subscriptions; config = per-tenant cartridge/model/BYOK.
Self-host variant: same diagram with tenant = customer, shipped as Compose/Helm (api + worker + postgres + minio + redis); users still need identity, model code still needs the sandbox, secrets still must not enter it, runs must survive a container restart. The sandbox runtime is the one hard requirement to document.

ORDERED MIGRATION FROM TODAY'S CODE:
1. Scrub the sandbox env: `inherit_env=False` + explicit allowlist in `envs/kernel.py:87`; start the Jupyter kernel with a scrubbed env. Zero product impact. Do it today.
2. Bind `list_run_files`/`read_run_file` (`tools.py:178-207`) and `amend_tools` (`charts.py:411+`) to the caller's project via config; make every `/runs/{id}/*` route check project; stop the driver using the default env/workspace (`serve.py:305-308`). These are real bugs for non-default projects now.
3. Add a principal (static bearer / oauth2-proxy header first) threaded into every route and into `configurable`; unknown thread → 401; delete the "→ default" fallback (`sessions.py:66`).
4. Postgres for metadata (projects, sessions as message rows, runs index, gate decisions, usage ledger) with tenant_id + version; run.json stays the worker's working copy; `dsagent migrate` for the legacy layout.
5. Extract the worker: `dsagent worker` runs `WorkflowRunner` directly (CLI path), pausing at gates; `/runs/{id}/start|gate|stop` become queue/DB writes; delete the orchestrator-wrapped driver and `_walk_past_decided_gates`; chat `run_workflow` enqueues.
6. Events and control off the filesystem: `on_event` → stream, SSE subscribes, stop flag in DB.
7. Object storage for datasets/workspaces/artifacts; signed URLs; artifacts on their own origin; retention + delete API (replace the 409 in `api.py:246-268` with an audited delete).
8. Sandbox tier: implement SandboxBackendProtocol on a hardened runtime or hosted provider; kernel inside it; egress policy; enforce Step.timeout and budgets; per-thread chat sandboxes with TTL; remove the host docker-socket dependency.
9. Quotas + metering + BYOK; cartridge registry with per-project resolution; observability; audit log; remove the `globals()` hack (`serve.py:278-279`) and split api/serve routers.
Steps 1–3 keep the product's shape; 4–7 are the scale-out; 8 is the security floor for hosting other people's code; 9 is what you bill on.

TOP 5 BLOCKERS:
1. No identity/authorization; the client chooses tenant, project, session and run (`serve.py:288`, `api_projects.py:93-116`, `api.py:227-241`, `projects.py:77-93`).
2. LLM-generated code runs on the API host with the platform's secrets and unrestricted FS/network; the Docker env is not a boundary either (`kernel.py:87`, `local_shell.py:196-231`, `docker.py:99-120`).
3. Runs execute inside the API process (daemon threads, `driver.py:310-316`) or inside the SSE request (`tools.py:164`); no worker tier, no timeouts/budgets — a 4h GPU fit dies on the first deploy.
4. Live state in-process and on local disk — cached agents/kernels/InMemorySaver (`serve.py:254-272`), SQLite checkpoints in a workspace (`serve.py:393`), events.jsonl polling (`api.py:441`) — cannot run two replicas or survive a restart.
5. Cross-project reach: run-reading and amend tools ignore the store, the driver's orchestrator uses the default env/workspace for every launcher run, `default` is a shared catch-all with guessable run ids (`tools.py:178-207`, `charts.py:436`, `serve.py:305-308`, `api.py:151`).

PHASED PATH:
Phase 0 — safe to demo to a design partner (weeks): one dedicated VM per partner; `dsagent serve` bound to localhost behind oauth2-proxy/Cloudflare Access with TLS; a per-deployment LLM key with a hard spend cap; migration steps 1–2 landed (env scrub; tools/routes bound to project; driver env per project); CSP on `/projects/{id}/files` + TrustedHost; nightly backup of `.dsagent/`; documented "one trust domain per VM" rule and never `--host 0.0.0.0` without the proxy. Say plainly to the partner that their users share one trust domain and model code runs on that VM.
Phase 1 — first paying customer (self-host, or a dedicated single-tenant cloud stack per customer): migration steps 3–7 plus the sandbox floor (8): built-in auth with users/roles and an audit trail of gate answers; worker tier with durable jobs and gate pause/resume; Postgres + object storage; sandboxed compute with egress policy, resource limits, enforced step timeouts, per-run cost cap; retention and delete; observability; versioned schemas with an upgrade path; Compose/Helm packaging. Physical isolation per customer keeps the tenant boundary trivially true while the code learns tenant_id.
Phase 2 — scale (shared multi-tenant SaaS): tenant_id on every row, path and metric; admission quotas and metering/billing; BYOK; sandbox pool with warm starts and per-tenant caps; kernel-in-sandbox chat sessions with idle TTL; event fan-out across replicas; per-tenant cartridge registry with signed versions and remote image builds; GPU scheduling lane; regional residency and per-tenant KMS; SOC 2 controls (audit log, access logging, encryption at rest, deletion SLAs).
